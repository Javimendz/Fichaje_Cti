# 🌐 Contexto Total del Proyecto: Sistema de Gestión RRHH

Este archivo define la arquitectura global para que Windsurf comprenda cualquier módulo existente o nuevo.

## 📂 Estructura de Módulos (Patrón Estándar)
Todos los módulos en `src/` siguen la misma estructura de NestJS:
- **Entities:** Modelos de base de datos (TypeORM).
- **DTOs:** Objetos de transferencia de datos con validaciones (`class-validator`).
- **Cont# 📑 Manual de Integración Universal (API Contract)

Este archivo define los estándares de comunicación entre el Backend y el Frontend de este proyecto. Windsurf debe usar estas reglas para generar código coherente en ambos lados.

## 1. 🔍 Descubrimiento Automático de Endpoints
Para entender cualquier módulo, Windsurf debe:
- **En el Backend:** Leer los archivos `*.controller.ts`. Los decoradores `@Get`, `@Post`, `@Put`, `@Delete` definen la URL y el método.
- **En el Frontend:** Buscar archivos en `src/services/` o `src/api/`. La estructura del JSON enviado debe coincidir con los `*.dto.ts` del backend.

## 2. 🛡️ Estándar de Seguridad y Multi-tenancy
- **Propiedad de Datos:** Todas las entidades (Horarios, Incidencias, Fichajes, etc.) están ligadas a un `empresaId`. 
- **Frontend:** Debe extraer el `empresaId` y `userId` del token JWT decodificado al hacer login y mantenerlo en el estado global.
- **Backend:** Extrae el contexto del usuario del objeto `request.user`. Jamás permitir que el frontend envíe un `empresaId` en el body para modificar datos; siempre debe validarse en el servidor.

## 3. 📤 Estándar de Envío de Datos (Write Ops)
- **DTOs como Fuente de Verdad:** Antes de programar un formulario en el frontend, Windsurf debe consultar el `Create*.dto.ts` correspondiente en el backend para conocer las validaciones (`@IsString`, `@MinLength`, `@IsEnum`).
- **Transformaciones:** Si una entidad tiene relaciones (como Horario -> Distribuciones), el Frontend debe enviar el objeto anidado completo si el Service del backend está preparado para manejar `cascade: true`.

## 4. 📥 Estándar de Recepción de Datos (Read Ops)
- **Normalización de Fechas:** El Backend siempre envía fechas en formato ISO u objetos Date. El Frontend es responsable de formatearlas usando una librería (ej. `date-fns` o `luxon`) según el idioma del usuario.
- **Soft Deletes:** Si un endpoint devuelve datos vacíos, Windsurf debe verificar si la entidad usa `DeleteDateColumn` y si el frontend debe solicitar explícitamente los "archivados" mediante un query param `?includeDeleted=true`.

## 5. 🚦 Gestión de Errores y Estados de UI
- **400 (Bad Request):** El Frontend debe mapear el array de mensajes de error de NestJS a los campos del formulario correspondientes.
- **401/403:** El Frontend debe redirigir automáticamente al login o mostrar un mensaje de "Acceso Denegado".
- **Carga (Loading):** Toda petición asíncrona en el frontend debe manejar un estado de carga para deshabilitar botones de "Enviar" y evitar duplicidad de registros.
